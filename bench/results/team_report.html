Evaluation report · September 2026

Typed decision models for enterprise workflows: Jev, Open-Jev and Needle 3

798 test cases per model4 use casespublic datasetsrun 22 Sep 2026

Summary

  • Jev (TypeSafe) is the clear leader. It was best or tied on all four use cases, averaging 90.6% accuracy. It could automate 70% of cases while keeping the automated answers ≥95% correct, and at ~150 ms per request.
  • Jev's confidence scores are reliable: when it says 80%, it's right about 80% of the time. That makes confidence thresholds usable for human-in-the-loop routing. The two open models' scores are much less reliable.
  • Open-Jev-2B is a credible self-hosted option for routing tasks (88% on triage, 99.5% on tool selection), but it fell well short on judgement tasks such as toxicity (58.5%).
  • Needle 3 isn't suited to classification. It is only competitive at choosing a function to call (95%), which is what it was built for.
  • Recommendation: pilot Jev on one routing workflow using our own data, pending a data-governance review. Keep Open-Jev as a self-hosted fallback to evaluate at the larger 9B size.

Why we ran this

Jev is a new kind of model that returns typed decisions: a choice from a fixed list, a yes/no probability, or a score. It does this instead of generating free text, so our code can act on the answer directly, with no parsing and no risk of invented output. Before building on it, we wanted to know two things. How accurate and trustworthy is it on the kinds of decisions enterprises automate? And can an open model we host ourselves do the same job?

What we tested

Four common enterprise use cases, each built from a public, labelled dataset. We used a fixed random sample of about 200 cases per use case, balanced across the answer categories. All three models received exactly the same inputs.

Model by model

Jev

Recommended to pilot
  • Most accurate on every use case, and the only model whose confidence scores match reality closely (calibration error 0.006–0.073).
  • Out-of-scope handling is strong: 84% of off-topic and near-miss requests correctly rejected, with 93% accuracy on the in-scope ones.
  • Toxicity is its weakest area: 78.5% accuracy, with 77% precision and 82% recall on toxic comments. Only 20% of cases are safe to automate at 95% precision there, so a guardrail would still need human review or a second check.
  • Consideration: data is sent to a third-party API. That needs a data-governance and vendor review before production use.

Open-Jev-2B

Self-hosted fallback · test at 9B
  • Close to Jev on routing (triage 88.4%, tool selection 99.5%), and it keeps all data in-house.
  • Weak at judgement: on toxicity it flags cautiously, so 87% of its flags are right, but it catches only 20% of toxic comments. Intent accuracy drops to 74.5%.
  • Over- or under-confident (calibration error ~0.25 on the classification use cases), so confidence thresholds would need tuning per use case.
  • Slow on a laptop: 0.5–2.6 s per request, because the fast code it uses on NVIDIA GPUs isn't available on a Mac. The authors report ~85 ms on an H100.
  • The larger 9B model reports better accuracy (97.5% vs 94.7% on its authors' held-out test). It needs a ~20 GB GPU, which a MacBook doesn't provide.

Needle 3

Not suited to classification
  • Built for a different job: picking and filling tool calls on phones and other small devices. On tool selection it chose the right function 95% of the time and got the arguments fully right 61% of the time.
  • Declined 28–55% of classification cases, and its confidence was often 0.9–1.0 even on wrong answers. That makes confidence thresholds unreliable.
  • Very small and fast (35 MB, 30–160 ms on CPU, works offline). Worth revisiting only for on-device agents that call tools.

Caveats

  • Public, not production, data. Real tickets are messier and specific to our domain. These results show relative strength, not the accuracy we should expect in production.
  • One run of ~200 cases per use case. Differences of 2–3 points are within noise. The large gaps (Jev vs Needle, and toxicity) are not.
  • Latency isn't like-for-like. Jev's time includes the internet round trip, Open-Jev ran on a laptop GPU, and Needle on a CPU. Treat the speed numbers as indicative only.
  • Prompts were not tuned. Every model got the same short instructions and category descriptions. Better descriptions would likely help all three, especially on toxicity.
  • Needle was used outside its design. Each classification was given to it as a tool to call, which is the closest fit its interface allows.

Recommended next steps

  1. Run the same test on our own data. 200–300 anonymised, labelled cases from one real workflow (support routing is the best candidate). The harness takes them with no code changes.
  2. Start a data-governance and vendor review for Jev: data residency, retention, what's covered by the contract, and pricing at our volume.
  3. Test Open-Jev-9B on a Linux machine with an NVIDIA GPU, to see whether a self-hosted option can close the gap with Jev on intent and toxicity.
  4. Tune the instructions for the toxicity guardrail, and consider a second check (another model or a human) for mid-confidence cases.
  5. Set confidence thresholds per workflow from the tuned results, choosing the precision target the business owner will accept.

Reproducing the results

Everything lives in JEV/bench/. Runs pick up where they left off and retry any failed cases. Results are written per case, so every number here can be traced back to a single prediction.

python build_datasets.py            # sample the four sets from public data
./run_local.sh                      # Needle, then Open-Jev (starts/stops its server)
python run.py --model jev           # needs TYPESAFE_API_KEY
python report.py && python make_chart.py

Metric definitions: accuracy counts declined answers as wrong. Calibration error is ECE over 10 bins, using the model's confidence in its chosen answer. Needle's tool arguments were scored against BFCL's accepted values.
